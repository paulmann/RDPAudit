# 95. Обновление парка RdpAudit (несколько машин одной командой)

Документ описывает канал управления, инструмент и то, что считается успехом. Замеры — 23.10.2026.

## 1. Состав парка

| Хост | Имя | Сеть | Служба | БД (23.10.2026) |
|---|---|---|---|---|
| 192.168.1.50 | SuperServer | Флотская | `RdpAuditService`, LocalSystem | 2,53 ГБ |
| 192.168.1.60 | Xeon | Флотская | то же | 293 МБ |
| 192.168.1.100 | MailServer | Флотская | то же | 1,16 ГБ |
| 192.168.3.100 | ILAB | ILAB | то же | 420 МБ |

Раскладка на всех — `C:\Program Files\RdpAudit\Service\RdpAudit.Service.exe` (single-file) и
`C:\ProgramData\RdpAudit\` (appsettings.json, rdpaudit.db, Logs, Backups). На 1.60 в папке службы
дополнительно лежат посторонние DLL от более ранней неудачной раскладки: single-file их игнорирует,
удалять не нужно, и обновление их не трогает.

## 2. Канал управления

SSH по ключу: `%USERPROFILE%\.ssh\id_zabbix_ops`, пользователь `md`, полные права администратора
(в SSH-сессии группа `BUILTIN\Administrators` — Enabled, не deny-only). Проверено на всех четырёх
машинах 23.10.2026.

Почему не SMB/SCM с этой рабочей машины: сохранённая учётка есть только для 192.168.1.50; на 1.100 и
3.100 `sc query` и `C$` отвечают отказом. SSH работает на всех.

Особенность 192.168.1.60: **ICMP закрыт штатно** (так настроено, Zabbix проверяет его по TCP 55554).
`ping` не отвечает — это не признак выключенной машины; проверять `Test-NetConnection -Port 22` или
сразу `ssh`.

## 3. Инструмент

`tools\Deploy-RdpAuditFleet.ps1` (pwsh 7.6, `#Requires -Version 7.6`, `#Requires -PSEdition Core`).

```powershell
# предполёт без изменений
.\tools\Deploy-RdpAuditFleet.ps1 -HostsFile .\tools\fleet-hosts.txt -DryRun

# обновление всего парка
.\tools\Deploy-RdpAuditFleet.ps1 -HostsFile .\tools\fleet-hosts.txt -Confirm:$false

# откат одного хоста на последний бэкап
.\tools\Deploy-RdpAuditFleet.ps1 -Hosts 192.168.1.60 -Rollback -Confirm:$false
```

Параметры: `-Hosts` (список, можно строкой через запятую), `-HostsFile`, `-PublishPath` (по умолчанию
`..\publish\Service`), `-IncludeDatabaseBackup`, `-StartTimeoutSeconds`, `-DryRun`, `-Rollback`.

Порядок на каждом хосте:

1. **Предполёт.** `sc query` → `RUNNING/STOPPED`, размер развёрнутого exe через `%~zA` (русская локаль
   печатает `dir` с разделителями разрядов — парсить его нельзя). Если размер совпал с публикацией,
   хост помечается `up-to-date` и не трогается.
2. **Бэкап папки службы** в `C:\ProgramData\RdpAudit\Backups\service-before-<stamp>`.
3. **Остановка** службы и ожидание `STOPPED`.
4. **Копия БД** — только с `-IncludeDatabaseBackup` и только при остановленной службе (WAL при чистой
   остановке схлопывается, копия консистентна без VACUUM/backup API). По умолчанию шаг пропускается:
   перед миграцией снапшот и так снимает инициализатор, а лишние гигабайты в Backups не нужны.
   Включать имеет смысл там, где снимают доказательную базу до правки, а не только до миграции.
5. **Доставка**: `scp` публикации в `C:\Windows\Temp\rdpaudit-stage-<stamp>`, затем `robocopy /E`
   в папку службы. Ничего не удаляется — поэтому откат это просто обратный `robocopy`.
6. **Запуск** и проверка **дописанных** строк лога: до старта считается число строк
   (`find /c /v ""`), после — читается только хвост (`more +N`). Требуется
   `Database initialization completed successfully` и отсутствие `Database migration failed`,
   `Database initialization refused`, `table is locked`, `Persist batch of`.

Любой сбой на шагах 2–6 возвращает службу в работу (там, где она уже была остановлена) и помечает хост
`failed` / `needs-attention`; команда завершается кодом 1. Журнал прогонов —
`%LOCALAPPDATA%\RdpAuditFleet\journal.jsonl` (JSON-строка на хост: до/после, SHA-256 сборки, каталог бэкапа).

## 4. Что считается успехом

- служба `RUNNING` после старта;
- размер развёрнутого exe равен размеру публикации;
- в дописанных строках есть подтверждение инициализации;
- нет `table is locked`, `Persist batch of`, отказов миграции;
- файлы БД (`rdpaudit.db`, `-wal`) обновляются, то есть приём идёт.

Проверять это надо не только отчётом скрипта: он читает лог, но не доказывает, что события пишутся.
Независимая сверка — `dir C:\ProgramData\RdpAudit\rdpaudit.db*` дважды с интервалом ~30 с.

## 5. Миграции: каждая машина — свой риск

Схема обновляется на каждом хосте отдельно, и объём работы зависит от того, что там стояло:

| Хост | Было | Миграций применено |
|---|---|---|
| 192.168.1.50 | 14.09.2026 | 3 (Stage17–19) |
| 192.168.1.60 | 14.09.2026 | 3 |
| 192.168.1.100 | 14.09.2026 | 3 |
| 192.168.3.100 | 12.10.2026 | 0 |

Инициализатор перед миграцией сам снимает снапшот в `Backups\<yyyyMMdd-HHmmss>`; при нехватке места
миграция не выполняется и служба не стартует — это предусмотренный отказ, а не сбой обновления.
Поэтому `-SkipDatabaseBackup` экономит время, но не отменяет требования иметь место на диске.

## 6. Чистка бэкапов

`tools\Clear-RdpAuditBackups.ps1` удаляет только payload БД (`rdpaudit.db`, `-wal`, `-shm`) из копий
обновления, сохраняя папку службы, снапшот продукта и мелкие снимки установки:

```powershell
.\tools\Clear-RdpAuditBackups.ps1 -HostsFile .\tools\fleet-hosts.txt -DryRun
.\tools\Clear-RdpAuditBackups.ps1 -HostsFile .\tools\fleet-hosts.txt -Confirm:$false
```

Правило: снапшот продукта (`Backups\<stamp>\db\rdpaudit.db` + `manifest.json`) не удаляется никогда —
это единственная точка отката схемы, её узнаёт Configurator. Если снапшота на хосте нет, чистка этого
хоста отменяется целиком. Прогон 23.10.2026 освободил 4,22 ГБ на четырёх машинах.

## 7. Откат

Полный откат хоста: `-Rollback` (берёт самый свежий `service-before-*`, возвращает папку службы,
запускает). Откат схемы БД — вручную: остановить службу, удалить `rdpaudit.db-wal` и `-shm`, вернуть
`rdpaudit.db` из `service-before-*` или снапшот инициализатора, запустить.

Бэкапы не удаляются автоматически: чистка — отдельное решение владельца.

## 8. Ловушки, проверенные на практике

- **`-Hosts a,b,c` при запуске через `pwsh -File`** приходит одной строкой: PowerShell не разбирает
  запятые в аргументах `-File`. Скрипт делит элементы по `,`, `;` и пробелам сам.
- **Русская локаль `dir`** печатает размеры с разделителями разрядов и неразрывными пробелами —
  в скрипте размер берётся через `for %A in (...) do @echo %~zA`.
- **`sc query` на локализованной системе** печатает `СОСТОЯНИЕ`, но слово состояния остаётся
  латинским (`RUNNING`), по нему и разбирается.
- **`more +N`** используется как «прочитать файл с N-й строки»; в неинтерактивной сессии не встаёт
  на паузу.
- **Ключ `id_zabbix_ops`** — общий для парка; при его смене правится `-KeyPath` (по умолчанию берётся
  из профиля, без переменных окружения).
- **Остановка службы на 1.100 (почтовый сервер) и 3.100 (ILAB)** прерывает сбор событий RDP на время
  обновления: 20–60 секунд на хост, у 1.100 дольше из-за копии БД 1,16 ГБ.

## 10. Блокировка через MikroTik на парке

Провайдер блокировки включается на каждом хосте отдельно: `RdpAudit.firewall.provider = MikroTik`,
секция `RdpAudit.mikroTik` указывает на роутер своей подсети. Правило, которое пишет служба:
`/ip/firewall/filter chain=input action=drop src-address=<ip> comment="RdpAudit …"`, в начало таблицы.

| Хост | Роутер | Транспорт | Учётка | Ограничение источника |
|---|---|---|---|---|
| 192.168.1.50 | 192.168.1.1 «flotskaya» (7.24.5) | HTTPS 443, сертификат `rest-api` из их PKI | `rdpaudit` | `.50`, `.60`, `.100` (в `address` учётки) |
| 192.168.1.60 | тот же | тот же | тот же | тот же |
| 192.168.1.100 | тот же | тот же | тот же | тот же |
| 192.168.3.100 | 192.168.3.1 «ilab» (7.24.5) | HTTP 80 | `rdpaudit` | `192.168.3.100/32` |

На ilab HTTPS не поднят: порт 443 занят службой `reverse-proxy`, а `www-ssl` выключен. Пока используется
HTTP, ограниченный одним адресом источника; для перехода на TLS нужен свободный порт (например 4443)
и сертификат с рабочим ключом.

### Белый список и режим провайдера (23.10.2026, после включения блокировки)

При включении MikroTik белый список блокировки оказался пустым на всех четырёх хостах:
любая тревога с внутренним адресом ушла бы правилом на роутер. Прописано
`firewall.whitelist = 192.168.0.0/16, 10.255.255.0/24` — те же диапазоны, с которых роутеры
разрешают ssh и winbox. Это белый список **блокировки**: тревоги по внутренним адресам
по-прежнему создаются, но IP из этих диапазонов не отправляется в блокировку.
`alerts.whitelistIps` намеренно не заполнялся — он подавляет сами тревоги и скрыл бы перебор
изнутри.

Провайдер переведён в `Both` (Windows + MikroTik последовательно). Причина: одиночный `MikroTik`
означает, что правила `netsh` на самой машине больше не создаются, то есть переход снял локальную
защиту, которая была до него.

Открытый вопрос (решение владельца): `mikroTik.filterChain` остаётся `input`. Цепочка `input` —
трафик, адресованный самому роутеру, поэтому правило закрывает роутер, а не RDP-сервис: запрос
к серверу идёт через `forward`. Атака из той же подсети через роутер не видна вовсе — её закрывает
только брандмауэр машины, который теперь включён режимом `Both`.

Инструменты: `tools\Set-RdpAuditWhitelist.ps1` (правит только `firewall.whitelist`),
`tools\Set-RdpAuditProvider.ps1` (правит только `firewall.provider`). Оба снимают отпечатки
остальных секций и откатывают файл при расхождении.

### Цепочка переведена в forward (23.10.2026)

`mikroTik.filterChain = forward` на всех четырёх хостах (`tools\Set-RdpAuditFilterChain.ps1`).
Цепочка `input` закрывала только сам роутер: запрос к RDP-серверу проходит через `forward`, и
правило в `input` его не видит. Следствие, которое надо держать в голове: правило в `forward`
режет **весь** трафик с этого адреса через роутер, не только RDP.

Проверено на ilab запросом из службы: правило с `chain=forward` создаётся, встаёт на позицию 0 —
до разрешающих правил, включая собственное правило роутера `DROP RDP blacklist - FORWARD`
(позиция 10), поэтому конфликта с ним нет.

### Первые реальные срабатывания

Оба правила создала сама служба, то есть цепочка «тревога → правило на роутере» на парке работает.

| Роутер | IP | Цепочка | Итог |
|---|---|---|---|
| ilab | 192.168.31.100 | input | ложное: рабочая станция администратора, причина `BRUTE_FORCE_NTLM`. Правило снято, SSH к роутеру восстановился |
| flotskaya | 91.245.149.108 | input | внешний адрес, причина `BRUTE_FORCE_NTLM`; адрес при этом лежит в списке `RU` и в `PORTAL_LOGIN` (пользователь портала) — вероятное ложное срабатывание, срок 1 час истекает сам |

Оба сработали до того, как был прописан белый список, — то есть ровно тот риск, ради которого он
и нужен. Детектор `BRUTE_FORCE_NTLM` считает неудачные NTLM-проверки; адреса из `192.168.0.0/16`
и `10.255.255.0/24` теперь в блокировку не попадают, но тревоги по ним продолжают создаваться.

### Включение на хосте

```powershell
.\tools\Test-RdpAuditMikroTik.ps1 -Gateway 192.168.1.1 -UserName rdpaudit -Password <секрет>
.\tools\Set-RdpAuditMikroTik.ps1  -Gateway 192.168.1.1 -UserName rdpaudit -Password <секрет>
# для ilab: -Gateway 192.168.3.1 -Port 80 -UseHttp
sc.exe stop RdpAuditService ; sc.exe start RdpAuditService
```

`Set-RdpAuditMikroTik.ps1` правит только `mikroTik` и `firewall.provider`, снимает отпечатки остальных
секций и откатывает файл, если хоть одна из них изменилась; перед записью кладёт
`appsettings.json.bak-<метка>`.

### Откат

1. Восстановить `appsettings.json.bak-<метка>` (там `provider = Windows`) или выполнить
   `Set-RdpAuditMikroTik.ps1` с прежними значениями.
2. Перезапустить службу.
3. На роутере удалить учётку и группу: `/user remove [find name="rdpaudit"]`,
   `/user group remove [find name="rdpaudit"]`. Правила блокировки снимаются сами по истечении срока
   либо вручную: `/ip firewall filter remove [find comment~"RdpAudit"]`.
